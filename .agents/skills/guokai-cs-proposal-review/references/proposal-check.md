# 开题报告核查项 K1—K10（必查，逐条给判定与证据）

每项给"通过／不通过／不适用"＋证据（栏位、段落、原文片段或脚本输出）。任一项不成立都进问题清单，不得以"方案基本可行""格式基本规范"概括通过。脚本命中须逐条给"成立/误报及理由"。分级：严重＝不改无法开题或触发硬门槛；重要＝影响 80 分/答辩或按期完成；一般＝文字与格式。

## K1 题目质量与撞题（严重/重要）

查法：
1. 是否本专业（计算机应用/系统开发/算法/硬件）；非本专业直接严重。
2. 对照五类问题（假/大/空/偏/旧，见 requirements 第三节）；"X 技术在 Y 中的应用研究"句式默认要求给出具体数据、任务、算法、指标，答不出即"空"。
3. 对照往年重复题目榜；命中即要求改题或加差异化技术点。
4. **批次撞题**：读项目记忆中本学期选题评审记录，比对业务领域＋核心判定逻辑＋技术栈；同业务同流程即撞题，须一人换题或互斥划界（划界声明写进开题报告）。
5. 题目是否体现内容核心：内容已改造（加了异常判定/派单/状态机等）而题目仍是通用原题→重要问题，给出推荐新题（含技术记忆点）。
6. 有前轮选题评审意见的，逐条核是否落实；未落实项重新列出。

不合格示例：停车场收费管理（命中重复榜）；失物招领批次第 3 题；协同过滤用在"发布—认领"一次性交互上（无行为矩阵，算不出指标）；内容已是"异常判定＋派单＋验收"而题目仍叫"设备点检系统"。

## K2 表单与封面完整性（重要/一般）

查法：五栏齐全（脚本识别＋人工核栏名）；封面姓名/学号/年级专业与学籍一致；题目与正文一致；**第5栏不得预填**（脚本检测，预填→一般问题，清空由教师填写签名）；表单模板未被自行改动（字号/加粗差异属模板固有，不列问题）。

## K3 研究现状与需求来源（第1栏）（重要）

查法：
1. 有无国内外研究现状综述（栏目明确要求"研究现状、水平和发展趋势"）；只有意义与方案→重要问题，要求用已有文献补 300—500 字：现有系统做法→不足→本题切入点。
2. 行业断言（"大量企业只是…""现象普遍"）有无文献标注；无→加引用或改限定表述。
3. 需求/数据来源是否交代：在岗/实习单位写明；否则改"参照行业通用配置"＋模拟数据并注明。调研对象学生不可达（非该行业在岗）→改公开资料＋访谈抽象建模，或换可接触的行业。
4. 研究目标是否可验证（有指标、有对比基线），不写"提升管理水平"式空目标。

## K4 技术路线可行性（第2栏）（严重/重要）

查法：**把核心承诺逐条当答辩问题审**——每条问"这在技术上成立吗？边界在哪？"
1. 承诺过强：二维码扫码≠到场证明（可拍照转发远程代扫）；"强制/杜绝"类措辞→改"提高作弊成本、留存可追溯证据"，并补到场校验（定位围栏/动态码）或诚实记录能力边界。
2. 实质矛盾：脱敏后承诺数值汇总统计（掩码/哈希后无法求和）→分类处理（标识类确定性脱敏保关联、数值类泛化＋先聚合后脱敏/授权白名单）。
3. 概念误用：数据分级依数据自身属性与泄露危害定级（GB/T 43697），与访问者角色/场景无关；角色×场景属"策略"不属"分级"。自造打分标准须说明依据国标哪些分级要素。
4. 算法前提：推荐/协同过滤须有累积式 user-item 行为数据；数据源涉隐私拿不到→定死公开数据集或规则化模拟数据并在论文注明；须有 Precision@K/Recall@K＋基线对比，否则仍是调库。
5. 前后端/字段描述矛盾（同一功能两处说法不一）→并入 K10，改法统一。
6. 研究方法是否与目标匹配（文献研究/需求分析/原型/测试各司其职）。

不合格示例（真实案例）："强制校验到场真实性"（二维码可转发）；"保留工资汇总统计"与薪酬脱敏并存；"字段敏感度评分同角色、场景相结合的分级模型"。

## K5 技术栈时效与术语（重要）

查法：脚本给已知 EOL/命名命中清单，人工逐条确认并补查清单外项：
- EOL：Vue2（2023-12-31）、Python 2、AngularJS 1.x、.NET Core 品牌止于 3.1；新项目选 EOL 技术与"技术选型原则"自相矛盾。
- 命名：".NET Core 8"→".NET 8/ASP.NET Core"；MySql→MySQL；Uniapp→uni-app；SpringBoot 规范写法。
- 术语：SignalR 是实时通信框架非"中间件"；其他把框架/库/协议混称的表述。
- 版本组合：Spring Boot 3 须 JDK 17+；论文声称版本互相矛盾。
改法写到具体小节与替换词，全文（题目、提纲、第2栏）同步。

## K6 工作量与写作聚焦（重要）

查法：
1. 亮点数量：并行"写深"的技术点 ≤1—2 个；五个亮点都写深不现实→指定一个技术记忆点写深（如派单规则引擎：规则表、匹配策略、兜底），其余作为支撑功能描述，**功能不砍、写作聚焦**。
2. 工期核算：按第2栏分步日期核算开发项数/天数（如后端 5 天排 8 项核心→失真）；给分批建议（先核心判定＋流转，再派单＋推送）。
3. 开发与写作并行风险：初稿截止时系统未完成→初稿先写前 4 章，第 5—6 章后补，节点不变。
4. 不申请学位（60 分口径）主动降配：砍并发基线对比、热更新降手动刷新、可逆映射降加盐哈希等；保留核心闭环与测试。
5. 测试时间必须留出；不得砍测试章。

## K7 提纲结构与观测点承诺（第3栏）（重要/一般）

查法：
1. 6—8 章、编号连续、体例单一（脚本核两种体例）；章角色覆盖（绪论/技术/需求/设计/实现/测试/总结）。
2. **核心亮点显性化**：核心创新须有显性小节（"4.4 阈值判定与派单规则流程设计"），不得淹没在"关键流程设计""核心模块实现"通用节名；实现章列明具体模块。
3. 观测点产出承诺（脚本给清单）：功能结构图、用例描述表、E-R 含基数、活动图/顺序图、测试环境与条件、关键代码含注释等；缺失→补明承诺，初稿必须出实物。
4. **提纲级追溯链**：抽 1—2 个核心功能，核需求→设计→实现→测试四环在提纲是否都有落点；断环写清断在哪环（如旁路防护缺需求条目、审计缺实现小节）。
5. 技术章与设计/实现章划界：技术章讲原理与选型对比，设计/实现章讲本系统模型与代码，防重复。
6. 非功能指标可测（"兼容性"→"支持 Chrome/Edge 最新两个大版本"）。

## K8 参考文献（第4栏）（重要/一般）

查法（脚本给条数/年份/外文/编号/类型标识，人工逐条复核）：
1. ≥5 条（表单底线）；建议按论文标准 ≥10 准备。
2. 近 5 年过半；外文 2—3 篇（开题可暂缺，列"初稿前补齐"）。
3. GB/T 7714 著录：缺类型标识/刊名/卷期页、机构名混作出版单位→逐条重录，给一条正确示例。
4. 编号体例统一（[1]–[n] 连续，部分缺编号→一般问题）。
5. 真实性抽查 2—3 条（知网/万方/官网/DOI）；已核实的写明出处，查不到写"未能核实"并要求学生提供检索链接或原文首页，否则替换。
6. 引用闭合：正文提及作者无条目（悬空）→补全或删除；列而未引→找落点或替换。开题无上标可宽松，初稿起必须。

## K9 进度 vs 学校节点（第2栏）（严重/重要）

查法：脚本逐条比对（阶段按步骤标题识别，查重子活动除外）；人工复核推断年份与一步多阶段。
1. 任一步骤晚于对应学校节点→列问题；**整体错位（初稿排到次年、跨度超 10 周）→严重问题，按节点倒排重写**，给倒排表（开题→初稿→修改稿→定稿→答辩→验收，含各阶段交付物）。
2. 倒排很紧时给降配前提（联动 K6）；再来不及砍前端界面数量，不得砍测试章。
3. 调研/数据准备排在初稿截止之后→前移或改公开资料路线。
4. 查重安排：初稿后摸底、定稿前终审属合理子活动，不判错位；定稿前重复率须 <30%。

## K10 全文一致性（严重/重要）

查法：
1. 题目—内容—技术路线—提纲—进度五者一致：题目承诺的核心在提纲有章、在第2栏有方案、在进度有工期。
2. 同一功能两处描述矛盾（前端水印 vs 后端水印、点检员ID vs 名称、题目 ASP.NET Core vs 提纲 .NET Core 8）→统一为一处正确表述，全文同步。
3. 术语统一（A5 漂移信号并入）；概念边界（分级 vs 策略、检测 vs 判定）前后一致。
4. 与批次互斥划界声明是否落实（联动 K1）。
